# 추가 수집 범위와 비용

**파일 캐시를 자동으로 찾아 추가 수집하는 기능은 제거하고, 실행 코드와 소켓에 남은 통신 내용은 유지했다.** 별도 옵션은 없다. 파일 처음이나 현재 읽기 위치의 몇 페이지만 고르는 기능은 실제로 필요한 파일 내용을 얻는다는 보장이 약했다. 이번 비교에서는 이 기능을 제거하자 추가 저장량과 CPU·메모리 사용량이 줄었다. 전체 수집 시간이 줄었다는 결과는 얻지 못했다.

## 남긴 범위와 제외한 범위

| 대상 | 수집하는 내용 | 남는 한계 |
|---|---|---|
| 실행 코드 | private 실행 영역에서 현재 RAM에 있는 ANON 페이지. 파일을 수정해서 생긴 별도 사본과 파일 없는 실행 코드 포함 | 파일 연결과 현재 쓰기 권한은 필수 조건이 아님. 정상 JIT 코드도 포함되므로 수집만으로 공격이라고 판정하지 않음 |
| 통신 | 프로세스의 FD → file → socket → sock → 큐/트리 → sk_buff → 실제 데이터 | 큐마다 최대 64KiB를 선택. 이미 사라진 통신과 전체 통신 이력을 복원하지 않음 |
| 파일 캐시 | 파일 처음·현재/직전 FD 위치·VMA 시작 위치를 찾아 추가 수집하던 경로 제거 | 일반 파일 내용과 FD를 닫은 memfd 내용을 추가로 확보할 가능성이 줄어듦 |

파일 이름·inode·매핑 등 커널 관리 자료를 고르는 기존 규칙은 유지한다. 덤프에 이미 들어온 캐시를 읽는 분석 기능도 유지한다. 예를 들어 sendfile로 보낸 파일 페이지를 소켓 버퍼가 실제로 참조한다면 그 페이지는 통신 근거로 추가 수집할 수 있다. 모든 파일 페이지를 강제로 제외하는 변경은 아니다.

실행 코드는 `/proc/<pid>/maps`에서 실행 구간을 찾고, `pagemap`의 실제 RAM 위치와 `kpageflags`의 ANON 표시를 확인한다. 소켓은 대표 task의 FD에서 찾으며 수신·송신 큐와 TCP 재전송·순서 외 수신 트리를 읽는다. 연속된 데이터뿐 아니라 페이지 조각과 `frag_list`도 제한 안에서 따라간다. 전역 소켓 표, 모든 스레드의 별도 FD 표, kTLS 키 추가 탐색은 이 범위 밖이다.

소켓 필드의 위치는 현재 실행 중인 커널의 BTF에서 읽는다. BTF는 커널 안의 자료가 어떻게 배치되어 있는지 알려 주는 정보다. 필요한 배치가 없으면 준비 검사 실패나 부분 수집으로 남긴다. 캐시용 Maple/XArray 탐색을 없앴지만, 다른 커널의 호환성까지 새로 검증한 것은 아니다.

## 내부 상한

코드와 네트워크는 합계 4,096개 후보 페이지를 나눠 쓰고 같은 물리 페이지는 한 번만 저장한다. 한 페이지가 4KiB이므로 **추가 본문은 최대 16MiB**다. 기존 규칙으로 이미 저장하는 페이지는 추가 본문 비용이 없다. 관리 자료 페이지도 후보 한도를 사용한다. 두 종류를 번갈아 선택하며 한쪽에 남는 몫은 다른 쪽이 쓸 수 있다.

이 상한은 전체 덤프, 연결·누락을 적는 `ranges.jsonl`, 수집기 메모리 사용량의 상한이 아니다. 코드는 프로세스 4,096개·실행 매핑 65,536개·참조 8,192개·유지하는 pagemap 256개, 네트워크는 task 4,096개·FD 참조 16,384개·소켓 4,096개·skb 8,192개·참조 기록 16,384개 등의 탐색 상한을 둔다. 네트워크가 최대 8,192개 후보를 찾더라도 최종 선택은 코드와 합쳐 4,096개 이내다.

추가 탐색 시간은 1초를 공유한다. 코드와 네트워크의 메타데이터 읽기는 각각 계상 한도 64MiB, BTF 파일은 64MiB로 제한한다. 코드의 실패한 일부 텍스트 읽기는 이 계상에 포함되지 않는다. 시간 한도는 다음 작업의 시작을 막으며 이미 진행 중인 커널 읽기나 저장 완료 대기를 강제로 끝내지는 않는다.

## 실제 확보한 내용

Ubuntu 24.04.5 / Linux 6.8.0-147, RAM 9GiB, 4 vCPU, ext4인 Kubernetes VM에서 이전 v6와 현재 v7을 비교했다. 기존 클러스터는 계속 실행했고 프로세스를 정지하거나 전역 캐시를 비우지 않았다. 바이트 분석에는 이번 부팅의 BTF·심볼·배너로 만든 ISF를 사용했다.

작은 입력은 TCP 32KiB·UDP 4KiB·32MiB 파일, 큰 입력은 sendfile 요청 1MiB·UDP 4KiB·128MiB 파일이다. 파일은 전체 내용을 쓰고 fsync했지만, 매 수집 시점에 파일 전체가 RAM에 남아 있는지는 따로 측정하지 않았다. 큰 TCP 요청 중 소켓이 받아들인 양은 490,012바이트이며 수신 큐에는 127,070바이트가 있었다. 이 양을 전체 전송 완료량으로 해석하지 않는다.

| 확인 대상 | v6: 코드·통신·캐시 | v7: 코드·통신 |
|---|---:|---:|
| 디스크를 그대로 두고 수정한 RX 코드 | 32/32페이지 일치 | 32/32페이지 일치 |
| 파일 없는 RX 코드 | 16/16페이지 일치 | 16/16페이지 일치 |
| 작은 TCP 수신 내용 | 32,768바이트 일치 | 32,768바이트 일치 |
| 큰 TCP 수신 내용 | 65,630바이트 일치 | 65,630바이트 일치 |
| UDP 수신 내용 | 4,096바이트 일치 | 4,096바이트 일치 |
| 확인한 일반 파일 캐시 위치 | 4페이지 중 3페이지 | 4페이지 중 0페이지 |
| FD를 닫고 매핑만 남긴 memfd | 16페이지 중 시작 1페이지 | 16페이지 중 0페이지 |

큰 TCP 큐는 양쪽 모두 61,440바이트를 확보하지 못했다. 큐별 선택은 65,536바이트이지만 물리 페이지 전체를 저장하면서 인접한 94바이트도 들어왔다. 작은 TCP와 UDP의 내용은 모두 일치했으며 시험 대상의 연결 정보도 수집 전후 같았다. 캐시와 memfd의 내용 손실은 이번 변경에서 받아들인 분석 범위 감소다. memfd 공유 관계 자체의 분석을 없앤다는 뜻은 아니다.

## 실제 비용 비교

두 실행 파일은 같은 Rust 1.93.0으로 만든 정적 musl 빌드다. 큰 입력의 같은 시험 프로세스를 유지하고 v6/v7, v7/v6, v6/v7 순서로 총 6회 수집했다. 아래는 각 3회의 중앙값이다. 시간에는 저장 완료 대기도 포함한다. CPU 시간은 사용한 CPU 시간을 합한 값이다. 최대 메모리는 실행 중 가장 컸던 RSS다.

| 항목 | v6 | v7 |
|---|---:|---:|
| 같은 수집의 페이지 속성으로 계산한 추가 본문 | 5.07MiB (5,312,512바이트) | 328KiB (335,872바이트) |
| 연결·수집 범위 기록 크기 | 9.80MiB | 4.80MiB |
| 최대 메모리 사용 | 20.91MiB | 11.25MiB |
| CPU 사용 시간 합 | 3.25초 | 2.61초 |
| 추가 자료 탐색 | 128.53ms | 46.17ms |
| 네트워크/캐시 연결 재검사 | 79.96ms | 1.67ms |
| 저장 완료까지 전체 시간 | 3.65초 | 3.74초 |
| HTTP 응답 p95 | 2.30ms | 2.14ms |
| HTTP 응답 p99 | 3.96ms | 3.17ms |

추가 본문은 약 93.7%, CPU 시간은 약 19.7% 줄었다. 추가 본문은 각 수집본의 페이지 속성에 기존 필터를 다시 적용해 계산했다. 실행 중인 노드의 전체 덤프 크기 차이를 새 기능의 비용으로 사용하지 않았다. 기록 파일 크기는 전체 `ranges.jsonl` 크기이므로 전부 캐시 제거만의 효과라고 단정하지 않는다.

**전체 수집이 더 빨라졌다는 근거는 없다.** v6의 전체 시간은 3.47~4.61초, v7은 2.87~3.77초였다. 저장 완료 대기 중앙값도 1.80→2.36초로 달랐다. 짧은 실행 3회씩의 결과이며 저장장치와 배경 작업의 영향을 분리하지 못한다. p95는 응답 100개 중 약 95개가 끝나는 시간, p99는 약 99개가 끝나는 시간이다. HTTP 오류는 9회 수집 모두 0이었지만 단순한 로컬 HTTP 시험이며 실제 서비스의 성능 보장은 아니다.

작은 입력은 한 쌍만 확인했다. 추가 본문은 5,206,016→233,472바이트(228KiB), CPU 시간은 3.10→2.76초, 전체 시간은 5.14→4.24초였다. 한 번씩의 확인값이므로 반복 성능 결과로 확대하지 않는다.

## 상한에 걸렸을 때

v7에서 파일 없는 실행 영역을 32MiB로 늘린 별도 시험을 했다. 발견한 후보 4,210페이지 중 4,096페이지를 선택했고 정확한 추가 본문은 16,445,440바이트(15.68MiB)였다. 전체 시간은 3.30초, 최대 메모리는 12.64MiB였다. 전체 상태는 `partial`이며 한도에 따른 누락을 남겼다.

이 시험에서 파일 없는 실행 영역은 8,192페이지 중 3,981페이지를 확보했지만 **수정된 파일 코드 32페이지는 모두 빠졌다.** 코드 탐색 순서와 코드 내부 후보 한도는 이번에 바꾸지 않았다. 캐시를 제거했다고 모든 코드 변조 증거를 먼저 확보하는 것은 아니다. 코드 우선순위를 개선하려면 별도 설계·검증이 필요하다.

일반 크기의 v7 수집 4회 중 2회도 다른 클러스터 프로세스의 네트워크 연결 정보가 바뀌어 `partial`이었다. 시험 프로세스의 확인한 참조와 바이트는 안정적이었다. 전후 값이 같아도 그 사이의 주소 재사용이나 내용 변경까지 배제하지는 못한다.

## 검증 범위

수집기 자동 검사 53개가 통과했다. 최종 정적 실행 파일로 큰 입력 3쌍·작은 입력 1쌍·한도 시험 1회, 총 9회 수집했다. 모든 수집본의 LiME 무결성·범위 기록을 검증하고 같은 수집의 정답 바이트와 대조했다. 무결성 검증 성공은 전체 자료를 수집했다는 뜻이 아니다.

실제 frag_list·순서 외 TCP·kTLS·컨테이너 탈출 전체 시나리오와 다른 커널 버전의 양성 검증은 이번 범위 밖이다. 시나리오 분석 스크립트는 시험에만 사용했고 공통 분석기의 main에는 넣지 않았다.

실행 파일 SHA-256: `e3ea35872ca5649c8c815cb4a273a4cd61dfbd94affefc1eccbf5961fd1456c2`. 개발 옵션 없는 정적 빌드이며 빌드에 사용한 소스 14파일을 대조했다. [실행별 수치와 근거](resource_retention_results.json), [이전 v6 결과](history_resource_retention_v6.md)를 함께 보존한다.
