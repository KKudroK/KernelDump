# Pod를 지정한 커널 수집

**`--pod`로 코드와 통신 내용의 추가 수집을 특정 Pod로 좁힌다.** 기존 커널 관리 정보의 수집은 유지한다. 수집 종류를 고르는 옵션은 늘리지 않았다. 파일 캐시 전체를 추가 수집하는 기능도 다시 넣지 않았다.

```sh
sudo ./kerneldump capture --pod <전체_Pod_UID> --output /evidence/new_collection
```

옵션을 생략하면 노드 전체에서 제한된 추가 수집을 수행한다. 지정한 Pod가 없으면 오류로 끝내며 노드 전체 수집으로 바꾸지 않는다. Pod 이름이나 짧은 UID는 받지 않는다.

## 대상을 확인하는 방법

1. 호스트의 PID·cgroup 네임스페이스에서 실행하는지 커널의 초기 네임스페이스 번호와 비교한다.
2. `/proc`의 cgroup 경로에서 전체 Pod UID가 들어간 경로 항목을 정확하게 찾는다. 같은 Pod의 여러 컨테이너와 sandbox도 포함한다.
3. PID뿐 아니라 프로세스 시작 시간, cgroup 경로, 부팅 식별 번호를 기록한다. Pod에 속한 스레드도 각각 기록한다.
4. 코드 페이지는 선택한 프로세스에서만 찾는다. 소켓은 선택한 스레드의 FD 표에서 찾는다. 같은 FD 표는 중복해서 탐색하지 않는다.
5. 읽기 전후 실행 식별 정보와 참조를 다시 확인한다. 마지막에 Pod 구성원을 다시 찾는다. 사라짐·교체·소속 변경·한도 초과는 누락 또는 불완전 수집으로 남긴다.

현재 cgroup 소속을 기준으로 한다. 호스트 마운트 네임스페이스로 들어갔어도 Pod cgroup에 남은 프로세스는 포함한다. 이미 Pod cgroup을 떠난 프로세스의 과거 소속은 이 옵션만으로 찾지 못한다. 순서대로 읽으므로 모든 값이 같은 순간의 값이라는 보장은 없다.

## 보존하는 자료

| 대상 | 수집 범위 |
|---|---|
| 실행 코드 | private 실행 영역의 현재 ANON 페이지. 파일을 수정해서 생긴 사본과 파일 없는 실행 코드. 현재 쓰기 권한은 필요하지 않음 |
| 통신 | FD → file → socket → sock → 대기 큐 → sk_buff → 내용 페이지. TCP 수신·송신·재전송·순서 외 수신, UDP reader_queue 포함 |
| 흩어진 통신 내용 | 연속 영역, 페이지 조각, 제한된 frag_list 연결 |
| 파일·공유 메모리 관계 | 기존 커널 관리 자료 선별 유지. 일반 파일 캐시나 memfd 본문을 별도로 모두 추가 수집하지 않음 |

UDP의 내용을 미리 확인하는 `MSG_PEEK` 뒤에는 데이터가 `udp_sock.reader_queue`에 남을 수 있다. 실제 검증에서 이 누락을 찾아 해당 경로를 추가했다. 구조체 위치는 실행 커널 BTF로 구한다. 필드가 없으면 임의 위치를 추측하지 않는다. [Linux UDP 구현](https://linux.googlesource.com/linux/kernel/git/torvalds/linux/+/54ac9ff8f1196afc49d644a1625e0af1c9fcf7f5/net/ipv4/udp.c).

코드·통신 후보는 중복을 빼고 합계 4,096페이지, 추가 본문 최대 16MiB를 공유한다. 관리 자료 후보도 이 한도를 쓴다. 큐별 내용 선택은 64KiB이고 추가 탐색은 협력적 1초 한도다. 진행 중인 커널 읽기를 강제로 끊는 시간 제한은 아니다.

Pod 구성원 탐색은 처음 1초·마지막 0.5초, 최대 65,536개 프로세스·4,096개 대상 스레드·32MiB 계상 읽기 한도를 둔다. 코드·네트워크별 소속 재검사는 각각 8MiB·250ms 한도를 둔다. 따라서 Pod 확인 비용까지 모두 기존 1초 안에 들어간다고 표현하지 않는다.

16MiB는 추가 본문의 한도다. 전체 커널 덤프, JSON 기록, 수집기 메모리의 한도가 아니다. 한 물리 페이지에 다른 대상의 내용도 함께 있을 수 있으며, `--pod`는 다른 Pod의 바이트를 완전히 배제하는 기능이 아니다. 같은 Pod 안의 큰 실행 영역은 여전히 중요한 코드 후보를 먼저 소모할 수 있다.

## 실제 시나리오 확인

Ubuntu 24.04.5 / Linux 6.8.0-147, 9GiB·4 vCPU Kubernetes VM에서 각 시나리오의 KernelDump를 한 번씩 수집했다. 이후 PodDump도 한 번씩 수집했다. 두 수집은 별도 시점이다. 같은 부팅의 ISF, Pod UID, PID·시작 시간, 전후 실제 값과 덤프 바이트를 대조했다. AWS는 사용하지 않았다.

| 시나리오 | 확인한 결과 |
|---|---|
| 코드 변조 | 부모가 자식의 RX 파일 매핑 1바이트를 수정. 디스크 해시는 유지되고 실행 결과 17→29. 수정된 4KiB 페이지가 KernelDump·Core 모두 일치 |
| memfd 공유 | 두 프로세스가 FD를 닫고 8KiB를 공유. i_mmap으로 두 프로세스를 찾음. 커널 덤프에는 본문이 없고 각 Core의 8KiB는 일치 |
| 평문 통신 | TCP 16KiB·UDP 4KiB 일치 |
| 애플리케이션 TLS | 실제 TLS 1.2 소켓의 남은 암호문 바이트 일치. 복호화 검증은 아님 |
| 프록시 형태 mTLS | 평문 연결과 상호 인증 TLS 연결의 내용 각각 일치. Istio/Envoy 배포 시험은 아님 |
| WireGuard | 실제 WireGuard 연결·암호화된 하위 구간을 확인. 소켓 평문 16KiB와 실제 frag_list 5개 연결을 대조. CNI 전체나 다중 노드 시험은 아님 |
| 자체 암호화 | 시험 자료를 XOR로 바꾼 뒤 전송. 소켓에는 바꾼 바이트가 그대로 남음. 실제 자료 유출은 하지 않음 |
| 호스트 영역 진입 | 시험 권한으로 호스트 마운트 네임스페이스에 들어가 전용 표식 파일만 열음. Pod 소속은 유지. 커널의 네임스페이스 번호와 실제 전후 상태 일치 |

별도 검증 Pod에서는 스레드 하나만 가진 UDP FD 표의 데이터도 확보했다. 잘못된 UID·중복 옵션·없는 Pod·호스트가 아닌 PID/cgroup 관점은 출력 폴더를 만들지 않고 거부했다. 수집기 자동 검사 59개, memfd 분석 회귀 검사 3개가 통과했다.

시나리오 분석기에서는 memfd 트리의 고정 필드 위치와 큰 페이지 내부 주소 계산을 고치고 읽기 실패를 기록했다. 호스트 마운트 번호가 같다는 사실만으로 호스트 출신 프로세스라고 단정하던 문구도 고쳤다. 이 스크립트들은 공통 분석기 main에 넣지 않는다. 네임스페이스 전환 자체는 시험 전후 기록으로 확인하며, 한 덤프만으로 과거 침해를 확정하지 않는다.

## 비용 비교

같은 시험 Pod를 유지하고 Pod 밖에 32MiB 실행 메모리를 둔 상태에서, 지정하지 않은 수집과 Pod 지정 수집을 순서를 바꾸어 각각 3회 수행했다. 아래는 중앙값이다. 측정 중 증거 전송이나 빌드는 실행하지 않았다. 커널 필터가 이미 고르는 페이지는 추가 본문 비용이 0이다.

| 항목 | Pod 미지정 | Pod 지정 |
|---|---:|---:|
| 추가 본문 | 15948.00KiB | 0.00KiB |
| 전체 명령 시간 | 9.81초 | 9.78초 |
| CPU 시간 합 | 8.52초 | 8.59초 |
| 최대 수집기 메모리 | 13.27MiB | 11.50MiB |
| 전체 범위 기록 | 9.99MiB | 7.34MiB |
| 저장 완료 대기 | 7.90초 | 8.06초 |

전체 시간은 9.81→9.78초, CPU는 8.52→8.59초였다. 이번 측정에서 속도나 CPU 사용량이 개선됐다는 근거는 없다. 대신 네트워크 탐색의 읽기 호출 중앙값은 14,304→816회, FD 확인은 1,643→19개로 줄었고, 대상 Pod 밖의 32MiB 실행 영역이 추가 수집 한도를 소모하지 않았다. Pod 구성원을 처음 확인하는 시간은 3.96~4.61ms였다.

전체 덤프 크기의 차이를 새 기능의 비용으로 쓰지 않았다. 추가 본문은 각 수집의 실제 페이지 속성에 기존 필터를 다시 적용해 계산했다. Pod 미지정 수집은 큰 외부 실행 영역 때문에 한도에 걸려 partial이었다. Pod 지정은 그 영역을 추가 후보로 선택하지 않았다. 일반 파일 캐시 전체를 추가 수집하는 경로는 유지하지 않는다.

이번 8개 시나리오에서 추가 본문은 코드 변조의 4KiB, 나머지는 0이었다. 나머지가 0인 이유는 시험 데이터의 페이지가 기존 선별에 이미 포함됐기 때문이다. 다른 입력에서도 추가 비용이 0이라는 뜻은 아니다. 통신 탐색은 실제 연결 근거를 남기고 기존 선별에서 빠진 참조 페이지를 제한 안에서 보완한다.

이 수치는 작은 단일 VM의 수집기 비용이다. 실제 서비스의 응답 지연·다른 커널·큰 Pod·높은 통신량의 성능을 보장하지 않는다. 저장 위치와 부하가 달랐던 과거 v7 수치를 이번 시간과 직접 비교하지 않는다. kTLS 키, 전체 과거 통신, 모든 패킷의 정확한 시간·누적 전송량은 검증하지 않았다.
