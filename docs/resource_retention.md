# Pod에 연결된 파일 캐시 수집

**일반 파일 캐시 전체는 수집하지 않는다. Pod를 지정했을 때 분석에 바로 쓸 수 있는 일부 내용만 보완한다.** 기존 `--pod`를 사용하며 새 옵션은 없다. 프로세스 메모리는 PodDump로, 파일·소켓과 연결된 커널 근거는 KernelDump로 확보한다는 역할을 유지한다.

```sh
sudo ./kerneldump capture --pod <전체_Pod_UID> --output /evidence/new_collection
```

Pod를 생략하면 v8의 제한된 노드 전체 코드·통신 수집을 유지하며 이번 캐시 탐색은 하지 않는다. 기존 커널 관리 자료의 선별은 어느 쪽에서도 유지한다. Pod 지정이 덤프 전체를 그 Pod의 자료로만 제한하는 것은 아니다. 정확한 Pod UID·cgroup 항목·PID와 시작 시간·스레드 목록의 확인 방법은 [v8 검증](history_resource_retention_v8.md)에 설명했다.

## 무엇을 추가하는가

| 대상 | 고르는 범위 | 분석에서 쓰는 방법 |
|---|---|---|
| memfd·tmpfs 파일의 앞부분 | 선택한 Pod가 FD를 열어 둔 파일의 앞 64KiB까지, 메모리에 남은 내용 페이지 | 프로세스에 매핑하지 않은 파일도 FD → 파일 → 실제 내용으로 연결 |
| 삭제 후 열린 파일의 앞부분 | 선택한 Pod의 열린 일반 파일 중 `i_nlink == 0`, 파일별 앞 64KiB | 이름이 삭제됐어도 열린 파일의 내용 확인 |
| 수정 실행 코드의 비교 자료 | 이미 찾은 private 실행 ANON 페이지에 대응하는 파일의 같은 위치 한 페이지 | 수정된 메모리와 현재 파일 캐시의 바이트 비교. 원래 파일이 커도 해당 위치만 찾음 |

FD는 프로세스가 열어 둔 파일의 번호다. FD만 있고 메모리 구간에 매핑하지 않은 파일은 Core만으로 전체 내용을 확보한다고 보장할 수 없다. 다른 프로그램 버퍼에 사본이 남아 있을 수는 있다. 이 경로는 파일 객체가 실제로 가리키는 내용을 보완한다.

비교용 캐시는 **현재 메모리에 남은 파일 내용**이다. 신뢰할 수 있는 최초 원본은 아니다. 차이가 있다는 사실만으로 공격이라고 판정하지 않는다.

## 구조를 따라가는 방법

대상 파일은 선택한 `task_struct`의 FD 표에서 `file`을 찾는다. `file.f_inode`에서 파일 종류·크기·남은 이름 수를 확인하고, `file.f_mapping`의 `address_space.i_pages`에서 해당 파일 위치의 페이지를 찾는다. 페이지가 다시 같은 `address_space`를 가리키는지도 확인한다.

코드 비교는 이미 찾은 수정 코드의 사용자 주소만 조회한다. `task_struct.mm`의 Maple Tree에서 그 주소의 `vm_area_struct`를 찾고, `vm_file`과 `vm_pgoff`로 파일 위치를 계산한다. 프로세스의 모든 메모리 구간을 다시 훑지 않는다. FD가 닫혔어도 이 연결이 남으면 비교 자료를 찾을 수 있다.

XArray의 루트·선택한 가지·페이지의 소속과 위치를 함께 확인한다. 여러 4KiB 페이지가 한 덩어리로 묶인 일반 folio는 요청한 위치만 계산한다. hugetlbfs는 이 경로의 검증 범위에 넣지 않고 미지원으로 기록한다. 필요한 구조 배치는 실행 커널의 BTF에서 읽는다.

내용은 `/proc/kcore`에서만 읽는다. 디스크 파일을 읽어 빠진 페이지를 메모리에 올리지 않는다. 값 항목이나 비어 있는 항목은 실제 파일 바이트로 바꾸지 않는다. 파일별 검사 결과·정책 제외·메모리에 없는 항목·읽기 오류를 구분해 남긴다. 읽기 전후의 연결 값과 실행 식별 정보를 다시 확인하지만, 내용 자체까지 한순간에 고정하는 수집은 아니다.

## 용량과 탐색 한도

| 항목 | 내부 제한 |
|---|---|
| 코드·통신·캐시 후보 합계 | 중복 제거 뒤 4,096페이지, 추가 본문 최대 16MiB |
| 캐시 후보 | 관리 정보 포함 256페이지, 최대 1MiB. 위 16MiB 안에서 사용 |
| 캐시 순서 | 코드·통신 탐색 후 실행. 코드·통신·캐시에 번갈아 후보 칸을 배정 |
| 캐시 탐색 시간 | 별도로 최대 100ms |
| 캐시 탐색 읽기 요청 | 최대 4MiB. 실행 커널 BTF 읽기 등 기존 준비 비용과 구분 |
| 캐시 작업 수 | FD·maps·VMA·COW 종류마다 최대 128개. 종류별로 번갈아 처리 |
| 파일별 보존 범위 | 파일별 앞 64KiB. 큰 파일도 확인한 앞부분을 보존 |

관리 정보도 후보 한도를 사용한다. JSON 기록·수집기 메모리 사용량·기존 커널 본문은 16MiB 본문 한도와 별개다. 후보·시간 한도에서 작업을 놓치면 `partial`이다. 파일 크기가 보존 범위보다 크면 원래 크기와 잘린 사실을 남긴다. 조건에 맞더라도 메모리에 없는 내용까지 확보한 것으로 표시하지 않는다.

## 기존 v8·v9에서 실제로 확보한 내용

Ubuntu 6.8 VM에서 같은 Pod와 시험 자료를 유지하고 v8과 v9를 번갈아 각각 3회 수집했다. 각 덤프의 무결성뿐 아니라 별도 분석기로 커널 연결과 바이트를 확인했다.

| 시험 자료 | v8 | v9 |
|---|---|---|
| FD만 열고 매핑하지 않은 memfd 12KiB | 해당 파일 페이지 미수집 | 12KiB 일치, FD·파일 연결 일치 |
| 삭제 후 열린 파일 8KiB | 해당 파일 페이지 미수집 | 8KiB 일치 |
| 수정 코드의 비교용 파일 페이지 4KiB | 비교 페이지 미수집 | 4KiB 일치. 수정 메모리와 정확히 한 바이트 차이 확인 |
| 기존 수정 실행 코드 4KiB | 일치 | 일치 |
| 기존 TCP 대기 내용 16KiB | 일치 | 일치 |
| 일반 파일, 128KiB memfd | 별도 캐시 후보 아님 | 정책대로 추가 후보에서 제외 |

큰 입력 시험은 64KiB memfd 160개와 일부 위치만 기록한 memfd, 파일의 1,337번째 페이지에 대응하는 수정 코드를 더했다. 없는 14개 위치를 없는 항목으로 구분했고, 먼 파일 위치의 비교 페이지도 맞게 찾았다. 캐시 후보는 256페이지에서 멈췄고 누락을 `partial`로 남겼다. 기존 코드와 TCP 내용은 계속 일치했다. 새 XArray 분류·큰 folio의 위치·공통 예산 우선순위 등을 포함한 자동 검사 65개도 통과했다.

## 비용

아래는 v9 수집 로직의 교차 3쌍 중앙값이다. 측정 중 빌드와 덤프 복사는 실행하지 않았다.

| 항목 | v8 | v9 |
|---|---:|---:|
| 전체 명령 시간 | 8.22초 | 8.49초 |
| CPU 사용 시간 합 | 8.13초 | 8.19초 |
| 최대 수집기 메모리 | 11.38MiB | 11.38MiB |
| 기존 필터에 더한 본문 | 4.00KiB | 28.00KiB |
| 전체 범위 기록 | 6.35MiB | 6.18MiB |

이번 작은 시험에서 캐시 기능으로 늘어난 본문은 **24KiB**다. 캐시 탐색 자체의 중앙값은 0.452ms였다. 전체 시간 중앙값은 0.27초 늘었지만, 실행별 흔들림이 있어 이 차이를 전부 캐시 기능의 영향으로 단정하지 않는다. 전체 살아 있는 커널 덤프 크기의 차이를 기능의 추가량으로 쓰지 않았다.

큰 입력 시험 한 쌍에서는 추가 본문이 8KiB → 620KiB, 최대 수집기 메모리가 11.38MiB → 12.45MiB였다. 전체 시간은 10.24초 → 9.28초였으나 한 쌍으로 속도 개선을 주장하지 않는다. 확보한 내용과 제한된 증가량을 근거로 이 범위는 유지한다. 일반 파일 캐시 전체, 큰 파일의 임의 일부, 디스크에서의 재읽기는 추가하지 않는다.

단일 VM·이 커널의 결과다. 서비스 응답 지연, 다른 커널·파일 시스템, 실제 큰 folio·hugetlbfs 수집을 검증한 것은 아니다. FD를 닫은 비실행 memfd 매핑의 내용은 이번 작은 FD 파일 경로에 포함하지 않는다. [기존 8개 시나리오의 v8 결과](history_resource_retention_v8.md)는 별도 이력이며 이번에 전부 재수행한 결과로 바꾸지 않는다.

비용 측정 뒤 수집 정책을 설명하는 manifest 문구에 캐시 예외를 명시했다. 수집 로직은 바꾸지 않았으며 소스 16파일을 대조해 이 문구와 한 호출의 줄바꿈 외 차이가 없음을 확인했다. 배포본으로 다시 수집한 FD-only memfd 8KiB도 내용·커널 연결·무결성이 일치했고 새 문구를 확인했다. 측정본과 배포본의 해시는 결과 파일에 따로 기록했다.
