# 원본과 현재 KernelDump 비교

여기서 원본은 익명 실행 페이지·소켓 큐·파일 캐시를 추가로 따라가 수집하지 않던 `kernel-focused-v4`다. 기존에 우연히 포함되는 페이지까지 전혀 없었다는 뜻은 아니다. 현재 배포본 `kernel-focused-v9`를 Pod 미지정·지정으로 나누어 같은 VM에서 비교했다.

Ubuntu 24.04.5 / Linux 6.8.0-147, RAM 9GiB, 4 vCPU, 같은 `/mnt/data` ext4 저장소에서 같은 시험 Pod를 유지했다. 실행 코드 수정 사본, 매핑하지 않은 memfd, 삭제 후 열린 파일, 일반 파일과 큰 memfd, 읽지 않은 TCP 내용이 남아 있는 상태다. 프로세스를 멈추거나 전역 캐시를 비우지 않았다. 세 구성을 순서를 바꾸어 각각 3회 수집했다. 측정 중 빌드나 증거 전송은 없었다.

원본과 현재 바이너리 모두 Rust 1.93.0 정적 musl 빌드다. 원본 비교본의 수집 코드·진입점·메모리 읽기·출력 안전 코드는 초기 Git HEAD와 같다. Cargo의 기능 선언과 별도 검증 명령에는 차이가 있으나 개발 기능은 꺼져 있고 측정은 capture 명령만 포함한다. 모든 이미지는 현재 배포본의 verify로 확인했다.

종료 전 노드 상태에는 디스크 공간 경고(`DiskPressure=True`)가 있었다. 시험 전후 실행 중인 Pod 11개와 재시작 횟수는 같았지만, 경고가 수집 시간에 미친 영향과 서비스 지연은 측정하지 않았다.

## 측정값

각 항목은 3회 중앙값이다. MiB는 1,048,576바이트다. 최종 덤프는 **압축하지 않은 LiME 파일의 실제 크기**이며 본문뿐 아니라 LiME 헤더도 포함한다. 원장·manifest 포함 행은 수집기가 만든 세 파일의 합계이고, 시험용 기록은 제외했다.

| 항목 | 원본 v4 | 현재 v9 · Pod 미지정 | 현재 v9 · Pod 지정 |
|---|---:|---:|---:|
| 수집 시간 | 10.11 s | 9.88 s | 9.72 s |
| 최종 LiME 파일 | 617.64 MiB | 615.01 MiB | 621.64 MiB |
| 원장·manifest 포함 | 622.97 MiB | 620.28 MiB | 626.58 MiB |
| CPU 시간 합 | 9.06 s | 9.90 s | 9.25 s |
| 최대 수집기 메모리 | 11.00 MiB | 11.25 MiB | 11.38 MiB |
| 기존 필터에 더한 본문 | 0.00 KiB | 8.00 KiB | 28.00 KiB |
| 수집 상태 | 완료 3/3 | partial 3/3 | 완료 3/3 |

Pod 지정 기준으로 **수집 시간은 10.11초 → 9.72초(-0.39초), 최종 덤프는 617.64MiB → 621.64MiB(+4.01MiB)**였습니다. 시간 범위는 원본 9.14~10.43초, Pod 지정 9.46~9.85초로 겹치므로 빨라졌다고 단정하지 않습니다.

전체 덤프 증가분을 모두 새 기능의 비용으로 해석하면 안 됩니다. 실행 중인 커널 상태가 달라지는 영향도 섞여 있습니다. 같은 수집에서 기존 필터에 실제로 더한 본문은 Pod 지정 시 **28KiB**, 미지정 시 **8KiB**였습니다. Pod 미지정 3회는 노드의 일부 통신 참조가 읽기 전후에 달라져 `partial`로 기록됐습니다. 9회 모두 저장 파일의 무결성 검증은 통과했으며, 무결성 통과와 참조의 일관성은 별개입니다.

이 수치는 작은 단일 VM의 관측이다. 큰 Pod·큰 파일·높은 통신량·다른 저장소에서 같은 비용을 보장하지 않는다. 후보 한도와 누락 조건은 [수집 범위](resource_retention.md)를 따른다. 기존 v8→v9 캐시 비교와 이번 v4→v9 비교는 다른 시험이므로 수치를 이어 붙이지 않는다.
