# 이전 v6 수집 범위와 비용

실행 코드·통신 대기 내용·파일 캐시의 선택한 부분을 하나의 수집 규칙에 넣었다. 새 사용자 옵션은 없다. 전체 캐시나 전체 익명 메모리를 넣으면 빠른 수집 목적을 지키기 어려워, 추가 후보를 합계 4,096페이지로 제한했다. 4KiB 페이지 기준 추가 본문은 최대 16MiB다.

## 어떤 내용을 고르는가

| 대상 | 읽는 연결과 선택 범위 | 남는 한계 |
|---|---|---|
| 실행 코드 | maps의 private 실행 영역 → pagemap의 상주 물리 페이지 → kpageflags의 ANON 확인 | 파일 연결·현재 쓰기 권한은 필수 아님. 정상 JIT도 포함. 실행 권한을 꺼 둔 과거 코드와 공유 shmem 코드 전체는 추가 대상이 아님 |
| 통신 | 대표 task → FD → file → socket → sock → 큐/트리 → sk_buff → 선형 바이트·페이지 조각·frag_list | 큐마다 64KiB. FD로 찾지 못한 소켓·이미 없어진 통신·kTLS 키 추가 탐색은 제외 |
| 파일 | FD 또는 VMA → file → address_space → i_pages XArray → page/folio | 파일 처음·현재/직전 FD 위치·VMA 시작 위치만 고름. address_space마다 최대 8개 위치. 전체 파일 복구가 아님 |

세 종류가 후보 한도를 나눠 쓰며 같은 물리 페이지는 중복 저장하지 않는다. 기존 정책에 이미 들어간 페이지에는 추가 본문 비용이 없다. 관리 구조체 페이지도 후보 한도를 쓰며, 한도가 남는 종류의 몫은 다른 종류가 쓸 수 있다. 새 본문 선택은 unsafe 또는 free 페이지를 다시 포함하지 않는다. 기존 정책의 보존 규칙 자체는 별개다.

탐색은 1초를 공유한다. 코드 쪽은 프로세스 4,096개·실행 매핑 65,536개·참조 8,192개·유지하는 pagemap 256개, 자원 쪽은 task 4,096개·FD 참조 16,384개·소켓 4,096개·skb 8,192개·참조 기록 16,384개 등의 내부 한도를 둔다. 자원 후보 8,192개를 찾더라도 최종 선택은 코드와 합쳐 4,096개 이내다. 코드와 자원 탐색은 각각 메타데이터 계상 64MiB를 사용하며, BTF 파일도 64MiB 이내로 읽는다. 코드의 실패한 일부 텍스트 읽기는 이 계상에 포함되지 않는다. 시간 제한은 새 작업 시작을 막는 제한이며 진행 중인 커널 호출의 종료 시각을 보장하지 않는다.

필드 위치는 실제 커널 BTF에서 읽는다. 지원하지 않는 필드를 추정 숫자로 채우지 않는다. 현재 자원 경로는 Maple VMA 트리와 대표 task의 FD/VMA를 사용한다. 모든 스레드의 별도 FD 표, 모든 커널 버전, 전역 소켓 테이블을 지원한다고 주장하지 않는다. BTF/필드가 없으면 준비 검사 실패와 부분 수집을 기록한다.

## 실제 바이트 확인

Ubuntu 24.04.5 / Linux 6.8.0-147, RAM 9GiB, 4 vCPU, ext4인 Kubernetes VM에서 확인했다. 기존 클러스터는 계속 실행했으며 프로세스를 정지하거나 전역 캐시를 비우지 않았다. 커널 배치는 같은 부팅의 BTF·심볼·배너로 만든 실험 ISF를 사용했다.

작은 입력은 TCP 32KiB, UDP 4KiB, 전부 기록하고 fsync한 파일 32MiB다. 큰 입력은 파일 캐시 128MiB와 sendfile 요청 1MiB다. 큰 요청 중 490,012바이트를 소켓이 받아들였고, 시험 수신 큐에는 127,070바이트가 남았다. 요청 크기를 실제 전송 완료량으로 바꾸어 쓰지 않는다. 파일 전체의 매 수집 시점 상주율은 별도로 측정하지 않았고, 실제 선택한 페이지의 상주·내용을 확인했다.

| 확인 대상 | 변경 전 | 변경 후 |
|---|---:|---:|
| 디스크는 그대로 두고 수정한 RX 코드 | 0/32페이지 | 32/32페이지, 바이트 일치 |
| 파일 없는 RX 코드 | 0/16페이지 | 16/16페이지, 바이트 일치 |
| 작은 TCP 수신 내용 | 0바이트 | 32,768바이트 일치 |
| 큰 TCP 수신 내용 | 0바이트 | 선택 범위 65,536바이트, 페이지 안의 인접 내용 포함 65,630바이트 일치 |
| UDP 수신 내용 | 추가 참조 없음 | 4,096바이트 일치 |
| 선택한 파일 캐시 위치 | 시험한 4페이지 중 0 | 처음·현재 위치·직전 위치의 3페이지, 12KiB 일치 |
| FD를 닫고 매핑만 남긴 memfd | 0/16페이지 | 시작 1페이지, 4KiB 일치 |

큰 TCP 큐의 나머지 61,440바이트는 확보하지 못했다. 파일 캐시의 마지막 페이지와 memfd 나머지 페이지도 전체 수집하지 않는다. 이는 전부 복원했다는 결과가 아니다. 수정된 시나리오 분석기는 큰 큐의 미수집 부분을 불완전 분석으로 표시했다.

## 실제 비용

같은 Rust 1.93.0·정적 musl 빌드로 변경 전/후를 비교했다. 크기별 3쌍을 순서를 바꿔 실행했고 아래는 각 3회의 중앙값이다. 시간에는 저장 완료 대기까지 포함한다. CPU 값은 두 작업 스레드가 쓴 시간을 합한 값이므로 전체 경과 시간보다 클 수 있다. p95는 응답 100개 중 약 95개가 끝나는 시간, p99는 약 99개가 끝나는 시간이다.

| 항목 | 작은 입력: 변경 전 → 후 | 큰 입력: 변경 전 → 후 |
|---|---:|---:|
| 저장 완료까지 시간 | 2.40 → 3.50 초 | 2.48 → 2.99 초 |
| CPU 사용 시간 합 | 3.01 → 3.42 초 | 2.94 → 3.47 초 |
| 최대 메모리 사용 | 11.12 → 22.79 MiB | 11.12 → 22.80 MiB |
| HTTP 응답 p95 | 2.00 → 2.18 ms | 2.11 → 2.14 ms |
| HTTP 응답 p99 | 2.52 → 2.79 ms | 2.64 → 2.83 ms |
| 연결·수집 범위 원장 크기 | 5.91 → 11.71 MiB | 5.36 → 11.57 MiB |

같은 수집 시점의 페이지 속성에 기존 필터를 적용해 계산한 **정확한 추가 본문**은 작은 입력 6,086,656바이트(5.80MiB), 큰 입력 6,193,152바이트(5.91MiB)였다. 별도로 원장 파일이 중앙값 기준 약 5.8~6.2MiB 늘었다. 전체 덤프 크기는 백그라운드 작업 때문에 달라지므로 두 덤프의 크기 차이를 새 기능의 비용으로 쓰지 않는다.

추가 탐색은 약 144~154ms, 자원 연결 재검사는 약 86~95ms였다. CPU 시간 중앙값은 약 14~18% 늘었고 최대 메모리는 약 11.7MiB 늘었다. HTTP 오류는 없었지만 단순 루프백 시험이며 실제 서비스의 성능 보장은 아니다.

전체 시간의 범위는 작은 입력에서 변경 전 2.32~2.98초, 변경 후 2.93~6.17초였고 큰 입력에서는 2.21~5.52초, 2.91~3.08초였다. 6.17초인 수집에서 저장 완료 대기만 4.34초였다. 따라서 시간이 거의 늘지 않았다고 단정할 수 없다. 이 VM에서는 수초 범위를 유지했지만 CPU·메모리·기록 용량 증가가 분명히 있다. 이 비용으로 전체 파일 대신 선택한 위치, 전체 통신 대신 큐별 짧은 범위를 확보하는 절충을 채택했다.

## 한도에 걸리는 경우

파일 없는 실행 영역을 32MiB로 늘린 시험에서는 후보 7,003페이지 중 4,096페이지를 선택했다. 정확한 추가 본문은 13,627,392바이트(13.00MiB)였고, 수집 시간 3.00초·최대 메모리 24.27MiB였다. 발견한 후보 중 2,907페이지를 선택하지 못했고 탐색도 후보 한도에서 멈췄다. 전체 상태는 `partial`이었다.

**이 시험에서는 수정된 파일 코드 32페이지와 시험 캐시 페이지도 빠졌다.** 현재는 전역 시간·용량을 지키는 수집이며, 큰 실행 영역이 있을 때 모든 중요한 증거의 우선 보존을 보장하지 않는다. 16MiB를 운영 부하를 막는 상한으로 채택했지만, 이 상한 안에서 모든 코드 변조를 분석할 수 있다는 뜻은 아니다. 빠진 프로세스 바이트는 PodDump의 별도 Core 범위도 확인해야 하며 두 입력을 같은 시점의 메모리로 합쳐서는 안 된다.

일반 크기의 최종 변경 후 6회 중 3회도 다른 클러스터 프로세스의 네트워크 참조 변화 때문에 `partial`이었다. 시험 프로세스의 확인한 참조와 바이트는 안정적이었다. 순차 수집에서 달라진 주소·길이를 숨기지 않으며, 전후 값이 같아도 중간 재사용이나 바이트 변경을 모두 배제하지 못한다.

## 검증 범위와 산출물

수집기 자동 검사 53개, 시나리오 코드 분석기 5개, 소켓 조각 분석기 4개가 통과했다. 최종 정적 바이너리로 일반 비교 12회와 한도 시험 1회를 수행했고 모든 결과의 LiME 무결성·범위 원장을 검증했다. 무결성 검증 성공은 수집 완전성의 뜻이 아니다. 실제 frag_list·순서 외 TCP·kTLS·컨테이너 탈출 전체 시나리오의 양성 검증은 이번 범위 밖이다.

실행 파일 SHA-256: `d3cd6ab5e415ffda7d2b8fe54b4fb29013cf12b59d185438d3c8f28b314338a5`. 소스 14파일의 빌드 해시와 배포 파일 해시를 대조했다. 개발 옵션은 포함하지 않았고, 공개 CLI에 새 옵션을 추가하지 않았다. [기계 판독용 결과](history_resource_retention_v6_results.json)에 실행별 비용·추가량·해시를 남겼다.

시나리오 전용 `detect_code_tampering.py`와 `recover_socket_queues.py`의 오류도 수정했지만 커널 분석기의 main에 넣지 않았다. 다른 두 시나리오 스크립트의 전체 정확도를 확인했다는 주장도 하지 않는다.

Linux의 원래 표현은 [pagemap 문서](https://docs.kernel.org/admin-guide/mm/pagemap.html), [XArray 문서](https://docs.kernel.org/core-api/xarray.html), [sk_buff 구조](https://github.com/torvalds/linux/blob/v6.8/include/linux/skbuff.h)를 참고한다.
